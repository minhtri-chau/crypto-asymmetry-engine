# Crypto Asymmetry Engine v9.2 — Historical Replay Engine

## What v9.2 does

v9.2 adds the first leakage-safe historical replay layer. It reconstructs only evidence that can honestly be reconstructed point-in-time from historical market data:

- asset price
- 7D / 30D return
- 50D / 200D moving averages
- price distance from those averages
- RSI-14
- 90D drawdown
- BTC 30D return
- asset 30D return relative to BTC
- simple trend state
- forward 7D / 30D / 90D return
- BTC-relative forward return
- MFE, adverse excursion and peak-to-trough drawdown

It deliberately does **not** manufacture historical Thesis Strength, Setup Evidence, protocol fundamentals, Market Regime, catalysts, qualitative research or AI assessments from today's information.

This is the foundation for later empirical calibration, not an automatic strategy optimizer.

## Deployment

1. Run `V9.2-MIGRATION.sql` in Supabase SQL Editor and append it to the end of the repo's existing `supabase.sql`. Do not replace `supabase.sql`.
2. Add `supabase/functions/historical-replay/index.ts`.
3. Merge `supabase/config-snippet.toml` into the existing `supabase/config.toml`:
   `[functions.historical-replay] verify_jwt = false`
4. Deploy the Edge Function named exactly `historical-replay`, JWT verification OFF.
5. Apply `patches/FRONTEND-PATCH.md` surgically to CURRENT `src/main.jsx`.
6. Push to `main` and let Vercel deploy.
7. Manually invoke the replay once before scheduling it.
8. Only after the manual run succeeds, optionally run `supabase/historical-replay-cron.sql`.

### Manual invocation

```sql
select net.http_post(
  url := (select decrypted_secret from vault.decrypted_secrets where name='project_url')
         || '/functions/v1/historical-replay',
  headers := jsonb_build_object(
    'Content-Type','application/json',
    'x-monitor-secret',
    (select decrypted_secret from vault.decrypted_secrets where name='monitor_cron_secret')
  ),
  body := '{"lookback_days":365,"cadence_days":7}'::jsonb,
  timeout_milliseconds := 30000
);
```

The returned integer is a pg_net request ID, not the HTTP status. Check Edge Function Invocations/logs and then the database.

### Verification SQL

```sql
select ra.symbol, count(*) replay_observations,
       min(h.observed_date) first_date, max(h.observed_date) last_date
from public.historical_replay_observations h
join public.research_assets ra on ra.id=h.research_asset_id
group by ra.symbol
order by replay_observations desc;

select ra.symbol, o.horizon_days, count(*) samples,
       percentile_cont(.5) within group(order by o.asset_return_pct) median_return,
       percentile_cont(.5) within group(order by o.btc_relative_return_pct) median_vs_btc,
       percentile_cont(.5) within group(order by o.max_drawdown_pct) median_max_drawdown
from public.historical_replay_outcomes o
join public.research_assets ra on ra.id=o.research_asset_id
group by ra.symbol,o.horizon_days
order by ra.symbol,o.horizon_days;
```

## Important limitations

CoinGecko history is used for this first replay layer. A 365-day replay cannot honestly reproduce old DefiLlama fundamentals, token unlock knowledge, qualitative web evidence or AI judgments unless those exact point-in-time datasets are separately reconstructed later.

The worker uses a weekly replay cadence by default to reduce overlapping samples and API load. Even weekly samples overlap at 30D/90D horizons, so sample counts are not independent observations. The UI calls them descriptive samples, not probabilities.

No existing deterministic threshold changes in v9.2.
